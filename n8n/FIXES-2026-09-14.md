# The nine reported failures — cause and fix

Reported by Anil, 2026-09-14. Each item below states what was actually found,
not what was assumed. Three of the nine turned out to have a different cause
than the symptom suggests, and one of them is the reason the other eight are
expensive.

**Status key:** ✅ fixed in this commit · ⏳ built, needs a rewire in n8n ·
🔶 needs a decision (see *Changes that need your go-ahead*)

---

## The one that costs money

Issues 2 and 3 are reported separately, and they are. But the damage comes from
the pair of them, and from two pieces of machinery that switch themselves off
at exactly the wrong moment.

**Airtable, `Sell Price`:**

```
IF(AND({Buy Price}, {Margin %}), ROUND({Buy Price} * (1 + {Margin %}), 2), {Buy Price})
```

With `Margin %` blank, Sell Price **is** the buy price. Not blank, not an
error — the cost price, silently, in the field the website and every email
read.

**Offer Dispatch, the leak guard in `Compose Email` and `Verify HTML`:**

```js
if (Number.isFinite(buy) && buy > 0 && (!Number.isFinite(sell) || Math.abs(sell - buy) > 0.005)) {
  // ... refuse to send if the buy price appears in the text
}
```

The guard that exists to stop the buy price reaching a client **only runs when
sell differs from buy**. When margin is missing, sell equals buy, the condition
is false, and the guard skips itself.

So "margin missing" + "Listing Approved ticked" does not fail loudly. It
publishes the cost price to akay.ie *and* mails it to clients, with the guard
that was supposed to catch it standing down because the two numbers agree.

Over a weekend that runs unattended for two days. This is the single most
important thing in this document.

## 1. Offers do not upload; fields missing; duplicate suppliers ⏳🔶

Three separate causes wearing one symptom.

**(a) One bad value bins ten offers.** `Create Offers` in the Excel and PDF
pipelines is set to `typecast: false` with Map Automatically. Airtable rejects
any value that is not already a choice on a single-select — and `Warehouse`
alone has 50+ ad-hoc options accumulated from supplier text. The Airtable node
writes in batches of 10, so one unrecognised warehouse rejects **the whole
batch**, and with `onError` unset the workflow then stops: the remaining
batches never run either. The Email pipeline uses `typecast: true`, which is
why its offers land.

🔶 Fix: `typecast: true` on both nodes, plus `onError: continueErrorOutput` so
a bad row is isolated instead of taking nine good ones with it.

**(b) Fields missing.** See issue 2.

**(c) Duplicate suppliers.** See issue 4.

## 2. Margin and auto-expiry applied to some rows but not all ✅⏳

Partly a consequence of 1(a) — rows 1–10 land, rows 11–20 are rejected, and the
batch that vanished is indistinguishable from "margin not applied".

The durable fix is that no pipeline should be *able* to write an offer with no
margin. `n8n/offer-invariants/enforce-offer-invariants.js` is one gate, shared
by all four pipelines, that holds any record missing a margin, a supplier, a
price, a currency or a name — writing it as `Hold` / `Pending Review` with the
reason in Notes rather than letting it go Live. Missing expiry defaults to 30
days, because an offer with no expiry never expires.

It deliberately **does not invent a margin**: `Apply Default Margin` already had
its turn with the supplier default and the 5% company default behind it.

✅ Node and tests written. ⏳ Needs wiring into the four workflows.

## 3. "Listing Approved" keeps being ticked automatically ✅

**It is not the pipelines, and it is not Airtable.**

- The Airtable base runs **zero** automations — confirmed against the API.
- Excel strips the field in `Expand Offers`.
- PDF has it in `READ_ONLY`.
- Email and WhatsApp delete it in `Offers to Create`.

Which leaves one writer: **an assistant calling the Airtable MCP directly**
while helping you process offers by hand. That matches the report exactly —
"it assures me it will never happen again and then repeats the action within a
couple of hours", and it is worst on manual processing, which is precisely when
that path is in use.

An instruction is the control that has already been tried and has already
failed, repeatedly. So the fix is not another instruction:

✅ `.claude/hooks/protect-airtable-fields.mjs` — a PreToolUse hook that
**blocks** any Airtable MCP call setting `Listing Approved` truthy or
`Send Approval Status` to Approved. It walks the entire tool input rather than
matching one argument shape, so a batch write, a different MCP server, `1`
instead of `true`, or a shape the hook has never seen are all refused. 14 tests
cover the ways past it.

Unticking is still allowed — that is how a mistake gets undone, and pulling an
offer off the site is never the dangerous direction.

⏳ One landmine remains: WhatsApp's `Build Airtable Payload` still contains
`if (autoApproved) fields['Listing Approved'] = true;`. It is currently
defused by a delete three nodes downstream. That line should go.

## 4. A different person at the same company becomes a new supplier ✅⏳

Found, and it is not that email domains are ignored — they are read, and then
thrown away:

```js
if (byDomain.has(domain)) byDomain.set(domain, null);   // "ambiguous"
```

A domain seen twice was discarded. Two records on `halitlar.com` are not an
ambiguity, they are two colleagues — so the moment a supplier had a **second**
contact on file, every *third* person there resolved to nothing and was
auto-created. Named `senderName || senderDomain || fromAddress`: the person.
One company, three records, three people's names, slightly wrong details.

✅ `n8n/supplier-resolver/resolve-supplier-identity.js` asks whether the records
on a domain are the same *company* rather than whether there is more than one.
Different companies on one mail host stay ambiguous and go to you — and no
third record is created.

## 5. A supplier in the email is not created ✅⏳

The real sender was only found behind a literal `-----Forwarded message-----`
or `Begin forwarded message:`. Outlook forwards, reply chains and "please see
below" all fail that test, leaving `fromAddress` as `offers@akay.ie`,
`externalSender` false, and nothing matched or created — with the supplier's
address sitting in the body four lines down.

✅ Addresses are now harvested from the whole body. A created supplier is named
after the **company** — a `Company:` line, a signature line ending in a legal
form, or the domain — never the person.

## 6. WhatsApp uploads with a blank supplier ✅⏳

`Resolve WA Supplier` matches on **phone digits and nothing else**. The sender
display name, the group name and the message text — which routinely carry the
company name, a website or a signature — were all ignored. Your read is right:
the information is there and it was being thrown away.

✅ All three are now evidence. And when nothing resolves, the resolver returns
`confidence: 'none'` and the invariant gate holds the offer, so a blank-supplier
offer cannot go Live at all.

## 7. Sending takes a long time and needs repeated approvals ⏳🔶

Two separate things:

- **The send itself.** `Send via Resend` posts one email per request, batched
  2 per 1.1 seconds. That is ~9 minutes per 1,000 recipients — the 1,232-
  recipient beer-portal send took about 11 minutes of pure rate-limiting.
  Resend's `/emails/batch` endpoint takes 100 per call. 🔶
- **The approval prompts.** Nothing was allowlisted, so every Resend and
  Airtable lookup stopped for a permission prompt. ✅ Read-only Resend,
  Airtable and n8n tools are now allowlisted in `.claude/settings.json`.
  **Sends are deliberately not allowlisted** — the content approval is the one
  prompt that should stay.

## 8. The text shown for approval is not the text that goes out 🔶

Not a bug — a design gap, and it explains why edits vanish rather than arrive
mangled.

`Compose Email` **rebuilds the body from Airtable fields on every run**, from
`Public Product Description`, `Price Display`, `Public Note`, `Public Terms` and
so on. There is no field anywhere on Offers that holds an approved body. The
approval step is a GET link (`?approved=true`) with no way to send text back.

So an edit made in chat is not lost in transit — it was never read. Meanwhile
the one-shot sends ("Nescafe Gold", "Corona & Peroni") send **raw verbatim
text with no template**. Two genuinely different templates, exactly as you
described.

🔶 Fix: an `Approved Offer Text` long-text field on Offers that `Compose Email`
prefers over its own template when present. You edit that one field; the
approval email and the client email then render from the same string, and the
existing `Verify HTML` check already proves the HTML matches it word for word.

## 9. Sending does not default to Resend ⏳

There is no rule saying it must, so the path is chosen per session. A hard rule
is now in `CLAUDE.md`: **every client-facing send goes through Resend from
`offers@akay.ie`** — never Gmail, never a new one-shot workflow when
`Offer Dispatch` will do.

## Changes that need your go-ahead

These touch production and are not applied. Say which you want.

1. **Airtable `Sell Price`** — make it blank when `Margin %` is missing,
   instead of falling back to `Buy Price`. This is the single change that makes
   "margin missing + approved over a weekend" impossible to publish at cost.
   Anything already relying on Sell Price being populated would show blank
   instead, which is why it is your call.
2. **Airtable `Public Listing`** — add `AND({Margin %})` so a margin-less offer
   cannot be publicly listed even if the box is ticked. Belt and braces with 1.
3. **Dispatch leak guard** — run the buy-price check unconditionally, so it
   stops standing down exactly when margin is missing.
4. **`typecast: true` + `onError: continueErrorOutput`** on the Excel and PDF
   `Create Offers` nodes (issue 1a).
5. **Wire the invariant gate** into all four pipelines, before `Create Offers`.
6. **Swap in the shared supplier resolver** on all four pipelines.
7. **Delete** `if (autoApproved) fields['Listing Approved'] = true;` from
   WhatsApp's `Build Airtable Payload`.
8. **`Approved Offer Text`** field + the `Compose Email` change (issue 8).
9. **Resend batch endpoint** in `Send via Resend` (issue 7).

5 and 6 should go out as the trade-terms normaliser did: dry-run branch first,
verified against a real batch, then switched over one pipeline at a time.
