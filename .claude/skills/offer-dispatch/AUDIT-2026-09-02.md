# Offer dispatch audit — 2026-09-02

**Question asked.** "Every time we send a sales offer there are errors; each time it is
'fixed for next time' and next time there are different errors. We don't change the
workflow, so something is wrong in the workflow or elsewhere."

**Answer.** The workflow *is* being changed — on almost every send day. `Offer Dispatch — Akay`
(`dAYMAj6mZD3hTV4T`) has **50 saved versions between 2026-07-30 and 2026-09-01**, all
authored "Anil Khetan (via MCP)", i.e. by the Claude session that was running the send.
Most of them were made *during* a dispatch, to get past that day's error. Each edit fixed
one thing and, several times, added a new failure surface that broke the next send. On top
of that, four external dependencies failed in the month with no monitoring (Resend key,
Anthropic credits, n8n execution quota, Airtable schema/records), and five throw-away
"one-shot" send workflows were built from scratch in the same period, each with its own bugs.
Nothing was actually stable enough to have "the same error twice".

The evidence, the fixes, and the rules that stop this recurring are below.

## 2. Root causes, ranked

### 2.1 The workflow is edited live, mid-send, on almost every send day
50 versions in 33 days. The pattern on a send day is: queue → run → error → edit the live
workflow → re-run → different error → edit again. There is no staging copy and no way to
exercise the workflow without emailing real clients, so every edit is tested on customers.
The regression suite and "source of truth" files the version notes refer to
(`.claude/skills/offer-dispatch/`) existed only on two side branches
(`claude/sales-offers-delivery-audit-behgfi`, `claude/zentner-spirits-airtable-f1mp91`) that
were never merged, so most sessions could not run them and re-derived the procedure.
The version note of 2026-09-01 09:37 says so in as many words: *"the repo source of truth is
not attached to this session, so this edit needs back-porting and test-nodes.cjs has not
been run against it."*

The 2026-08-27 change is the clearest example: a working text pipeline had an LLM
formatting step added to it after a successful send. That single node caused 4 of the next
9 runs to fail outright and 2 of the 4 that reached the model to fall back to plain text.

### 2.2 Four external dependencies with no health check before a send
- **Resend API key** became invalid on or before 2026-08-31 (three runs, 619 rejected sends).
- **Anthropic credits** ran out on 2026-09-01 (three runs blocked).
- **n8n Cloud execution quota** exhausted on 2026-08-14 (dispatch and backup lost).
- **Airtable**: a field deleted mid-run (08-04), Client records deleted mid-run (08-31 ×2).

None of these is a workflow bug, and none can be fixed by editing the workflow — but each
one produced a new-looking error on a send day, and each was "fixed" by a workflow edit.

### 2.3 Parallel, throw-away send paths
Five one-shot workflows in a month. The canonical method in Airtable says explicitly not to
build them. Each embeds its own audience, its own Resend call and its own log write, so each
fails in its own way and none of the dispatch fixes reach them.

### 2.4 Latent design gaps in the dispatch workflow itself (all fixed in this audit)
- **No idempotency on the Resend call.** With `retryOnFail` ×3 and overlapping runs, a
  timeout after Resend accepted the message, or two concurrent runs, could deliver twice.
- **The queue flag is cleared only at the end of the run.** Approval takes minutes to
  hours; a second run (manual or the 08:00 schedule) re-reads the queue and, because the
  choice is deterministic, picks the *same* group. 2026-09-01 came within a sort order of a
  1,277-recipient double send.
- **Halt alerts without a reason.** Only the gate nodes set `haltReason`; a declined
  approval and an all-failed send both arrived as "no reason recorded" — including the one
  alert that should have read "Resend rejected the API key".
- **The error handler's consequence line is fixed text**, "NO OFFERS WERE EMAILED", even
  when 507 emails had just been delivered and only the log write failed.
- **The HTML step depends on a metered third-party API** for pure formatting.

## 4. Rules that stop this recurring

1. **Freeze the workflow on send days.** No edit to `Offer Dispatch — Akay` while a run is
   in flight or an offer is queued. If a send fails, fix the *cause* (key, credits, data),
   not the workflow, and re-queue. Workflow changes happen on a non-send day, from the repo
   file, with the tests green, as one named version, published and verified.
2. **Pre-send dependency check (2 minutes, before queueing):** Resend key valid (send one
   pilot mail, or check the last run's Resend responses), today's Backup Registry row is
   *Verified*, n8n plan quota not exhausted, no Airtable schema change in progress. The
   `Weekly Health Check` catches these on Mondays; a send day needs it on the day.
3. **No more one-shot send workflows.** Any offer, any audience, goes through
   `Offer Dispatch — Akay` via `Queued for Dispatch`. If the targeting cannot express the
   audience, add the targeting field to the workflow (on a non-send day) — that is what
   `Excluded Countries` was.
4. **One run at a time.** Do not trigger a second dispatch while one is awaiting approval.
   The queue claim makes a second run safe, but it still splits attention across two
   approval mails.
5. **Read the approval mail before clicking.** It is the last point at which a bad offer
   can be stopped, and two of the month's "errors" were correct declines.
6. **Every edit lands in the repo first.** The n8n node header says so; from now on the
   folder is on the main working branch, so every session can run the suite.

## 5. Still open

- The **Resend MCP connector** in this environment is attached to a Resend account with no
  API keys, no domains and zero sends — it is not the account n8n sends through, so
  deliverability (bounces, complaints) cannot be verified from here. Point it at the right
  account or check the Resend dashboard directly.
- **n8n plan quota** (2026-08-14) can only be fixed on the plan.
- **Stale Client links** still cost the Sent Log rows of their own sub-batch when a Client
  record is deleted mid-run; the offer status is no longer affected (fixed 2026-08-31).
- The **3-day approval timeout** ends the run as *cancelled*, which the ERROR HANDLER does
  not see (n8n fires it on errors, not cancellations). The Weekly Health Check does.
- `preflight_dispatch.py` and `compose_preview.cjs` are restored but have not been run
  against a live export in this session.
